## 二、标准阅读

- **GM/T 0016—2023（SKF）**：第 7.1 节是设备管理，第 7.1.4 节 `SKF_EnumDev` 枚举设备名称，第 7.1.5–7.1.6 节是连接、断开，第 7.1.7 节 `SKF_GetDevState` 按名称查询设备是否存在，输入不是设备句柄。两者的返回码和输出参数要分开判断：`SAR_OK` 表示调用成功，不代表设备一定在位。
- **GM/T 0018—2023（SDF）**：第 6.2.2–6.2.6 节分别描述打开设备、关闭设备、创建会话、关闭会话和获取设备信息。`SDF_GetDeviceInfo` 接收**会话句柄**，按第 5.3 节向 `DEVICEINFO` 写入设备身份、版本、算法能力和缓冲区大小。附录 A 区分输入参数错误（`0x0100001D`）与输出参数错误（`0x0100001E`）。
- SKF 本次以名称查询设备状态；SDF 本次以会话句柄读取能力描述。接口对象不同，不能直接互换。

## 三、SKF：新增设备状态查询

**基线。** 从课程仓库 `ch06/longmaiskf0016-stu.zip` 取 `enumdevinfo/main.cpp`、SDK 头文件和 `skf/linux/x64/libgm3000.1.0.so`。原 Makefile 指向 x86 库，顶层 Makefile 改用 x64 库构建，不改原示例。`ldd` 确认程序可以找到 SDK。实际运行原例时退出码为 `139`，GDB 回溯到 `SKF_EnumDev → libusb_get_device_list → pthread_mutex_lock`。本机 WSL 看不到 USB 设备目录；这不足以确定厂商代码的根因。详见 [基线日志](logs/01-baseline.txt)。

**新增。** `skf/device_state.cpp` 实现设备状态查询：可直接传入设备名称，也可先枚举取首个在位设备名，然后调用 `SKF_GetDevState(name, &state)`。先检查返回码，再解析 `PRESENT`、`ABSENT` 或 `UNKNOWN`。实库版发现 USB 总线不可见时退出并提示，不把它解释成设备返回 `ABSENT`；模拟版单独链接测试桩，不作为厂商驱动使用。

```bash
make build/skf-state
bash tests/check-skf.sh
# 在能访问实体 UKey 的 Linux 环境运行：
./build/skf-state
./build/skf-state '枚举得到的真实设备名'
```

| 测试 | 实际结果 |
|---|---|
| SDK 版，当前 WSL 无 USB 总线 | 提示未调用厂商 API，退出 `3` |
| 模拟在位、离线、未知 | 分别输出 `PRESENT (0x00000001)`、`ABSENT (0x00000000)`、`UNKNOWN (0x00000002)` |
| 模拟查询失败、命令行参数过多 | 分别退出 `1`、`2` |

结果见 [SKF 验证日志](logs/02-skf-state.txt)。模拟通过只说明程序正确处理了这些返回分支。

**实体补测（Windows 与 openEuler）。** Windows SDK 先确认同一只 GM3000 在位，详见 [Windows 日志](logs/04-skf-hardware.txt)。随后用 `usbipd-win 5.3.0` 将 `055c:db08` 转接给 WSL，openEuler 安装 `kmod` 以提供 `modprobe`，加载 `usb_storage`。USB 已可见时，设备节点尚未就绪，立即查询仍找不到 Key；等 Longmai 的 SCSI 节点出现后重新验证：

| openEuler 实机测试 | 实际结果 |
|---|---|
| 课程原例 `skf-original` | 读到 `Manufacturer: Longmai`、`Label: GM3000`、容量 `131072` 字节；原源码固定返回 `1`。 |
| 新增查询 `skf-state` | `SKF_GetDevState` 返回成功，打印 `PRESENT (0x00000001)`，程序退出码为 `0`。 |

见 [openEuler 实机日志](logs/08-skf-openeuler-hardware.txt)（序列号已遮盖）。全程未改 PIN 或设备数据，测试后解除 USB 共享。

## 四、SDF：实现设备信息接口

**基线。** 课程仓库 `ch06/sdftest` 的 Makefile 为空；用顶层 Makefile 补充构建入口，编译原 `testsdf.c` 和 `sdf.c`。原测试输出“设备打开成功”“设备关闭成功”，退出 `0`，但两个接口直接返回 `0`，打开时也未写入设备句柄，因此不能把基线输出当成真实设备正确打开与关闭的证据。原例将 `int` 类型的 `LONG` 用 `%ld` 打印，编译器给出格式警告；基线构建用 GCC 的 `-ftrivial-auto-var-init=zero` 初始化局部变量，避免原程序传入未初始化的句柄。

**新增。** 保留原例作为对照，在 `sdf/src/device_info.c` 中复用课程 `sdf.h` 的类型，实现教学用设备和会话句柄，以及原头文件只有声明、没有实现的 `SDF_GetDeviceInfo`。调用次序：

```text
SDF_OpenDevice → SDF_OpenSession → SDF_GetDeviceInfo
              → SDF_CloseSession → SDF_CloseDevice
```

该实现只允许一个设备和一个活动会话；设备信息从软件结构体返回，不连接外部密码设备。不支持的算法及存储能力填 `0`，`StandardVersion=2` 是本示例按 §5.3 设置的字段值，不代表通过标准符合性认证。固定长度字段按字段宽度打印，避免依赖字符数组一定带有结尾零。

```bash
make build/sdf-info build/test-sdf
./build/sdf-info
./build/test-sdf
```

实际输出：设备名 `LAB3-SDF`，`DeviceVersion=1`，`StandardVersion=2`；打开设备、创建会话、查询、关闭会话与关闭设备均返回 `0`。传设备句柄代替会话、无活动会话、未关闭会话就关闭设备这三种情况返回 `0x0100001D`；空输出指针返回 `0x0100001E`。返回码与结构体断言全部通过。详见 [SDF 验证日志](logs/03-sdf-info.txt)。

**HSC32TU VPN 实机补测。** 用 `usbipd-win` 将 `096e:082e` 转接到 openEuler，等待 `/dev/bus/usb` 下对应节点出现，再运行 [补测脚本](tests/check-hsc32tu.sh)。早期在节点准备好之前调用，厂商库报枚举异常，`SDF_OpenDevice` 返回 `0x01000004`；等待节点后重试成功。脚本使用 `ch06/roceduhs0018sdfbak-tu.zip` 的 Linux x86_64 厂商库和头文件构建独立测试程序，没有链接软件模拟实现。

实机依次调用 `SDF_OpenDevice → SDF_OpenSession → SDF_GenerateRandom → SDF_CloseSession → SDF_CloseDevice`，五步均返回 `0x00000000`，成功请求 16 字节随机数，程序退出 `0`。随机字节未写入日志，未改 PIN 或设备数据，测试结束后解除 USB 共享。该 SDK 未声明或导出 `SDF_GetDeviceInfo`，因此这个自编函数仍以软件测试为证据；实机验证证明的是 HSC32TU 的 SDF 会话与随机数调用。见 [HSC32TU 实机日志](logs/09-sdf-hsc32tu-hardware.txt)。

## 五、问题与实验小结

本次最重要的区别是**编译成功、API 实际成功和硬件验证成功并不等价**。SKF 从无 USB 时的枚举异常，经过 USB 转接和等待设备节点，最终在 openEuler 实机验证通过。SDF 原例虽打印成功，但没有建立句柄；扩展后通过正向与异常用例验证了会话检查和释放顺序。本次未开展 4–6 学时的密码算法及密钥管理实现。
